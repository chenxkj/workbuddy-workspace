## 账号对标敌人

### 核心敌人：空泛鸡汤型职场博主

这类内容的典型话术：

- 年轻人别太在乎工资，先积累经验。
- 学历不重要，态度最重要。
- 努力就会成功。

老陈的反面定位：

| 对方 | 老陈 |
|:--|:--|
| 讲态度 | 讲交易结构、岗位需求和长期价值 |
| 讲空泛道理 | 讲研发总监真实筛选逻辑 |
| 让年轻人忍 | 让程序员看清自己的筹码 |
| 站在旁观者位置 | 站在面试官、技术负责人、过来人位置 |

**使用方式**：可以公开对标“某类现象”，不要点名具体博主。冲突句要打现象，不打个人。

### 隐性敌人：简历美化和造假包装型求职博主

这类内容的问题：

- 教人把没做过的项目包装成核心经历。
- 只追短期拿offer，不管入职后能不能扛住。
- 把真实能力建设替换成话术包装。

老陈的反面定位：

| 对方 | 老陈 |
|:--|:--|
| 教你包装 | 教你拿真实证据说话 |
| 追短期offer | 看三年后的简历价值 |
| 鼓励虚假经历 | 强调项目、问题、方案、结果 |
| 求职技巧号 | 研发总监筛人视角 |

### 使用边界

1. 不对标头部程序员大V，避免变成蹭热度。
2. 不把HR博主当主敌人，立场太散。
3. 不针对具体个人，只针对一类错误观点。
4. 每条冲突都要落回“程序员怎么做决策”，不能只吐槽。

### 试验线 E：技术外包避坑 + 产品落地拆解

定位：个人 IP 商业引流内容，用老陈“19年嵌入式、研发总监、做过真实产品和团队交付”的身份，吸引有开发需求的人来咨询。

当前决策：纳入账号内容计划，但不取代程序员职场主线。早期按小比例测试，用数据判断是否能带来有效咨询、私信和项目线索。

目标客户：

- 毕设、课程设计、小型技术项目需求方。
- 小企业老板、创业者、传统行业从业者。
- 有 App、小程序、上位机、嵌入式、硬件 Demo、机器人 Demo 需求的人。
- 有想法但不懂怎么拆需求、怎么找开发、怎么控成本的人。

内容目标：

- 建立老陈“懂技术、懂交付、懂老板想要什么”的信任感。
- 把泛流量转成私信咨询和项目评估。
- 为后续接单平台、合伙合作、案例库沉淀线索。
- 通过真实外包避坑和产品拆解，强化专业背书。

内容边界：

- 不做泛泛技术教学。
- 不做炫技。
- 不承诺低价快速万能交付。
- 不把账号直接变成硬广号。
- 不讲合作方、客户、项目的隐私信息。
- 不抢程序员职场系列的主要发布节奏。

#### 栏目 E1：技术外包避坑

作用：建立信任，筛选更懂规则、更愿意尊重交付边界的客户。

选题方向：

| 优先级 | 选题 | 判断 | 下一步 |
|:--:|:--|:--|:--|
| P0 | 为什么很多软件外包最后都会烂尾 | 痛点强，适合开系列 | 写成真实饭桌口吻，不做列表课 |
| P0 | 老板别一上来就问“做个 App 多少钱” | 容易引发咨询 | 写成需求拆解切口 |
| P0 | 外包报价太低，最后贵在哪里 | 强冲突，适合短视频 | 结合老陈签字/背锅经历 |
| P1 | 熟人开发也要写清楚交付范围 | 人情关系痛点 | 可和合伙边界内容联动 |
| P1 | 源码、部署、售后、维护，要不要写进报价 | 搜索价值高 | 做成咨询前筛选内容 |
| P2 | 怎么判断一个开发团队靠不靠谱 | 容易泛化 | 必须加真实判断细节 |

表达原则：

- 先讲真实场景，再给判断。
- 说客户听得懂的话，不堆技术名词。
- 重点讲需求、报价、验收、售后、源码、部署这些交易边界。
- 每条内容都要能自然引导到“先把需求拆清楚”。

#### 栏目 E2：产品落地拆解

作用：展示老陈能把“一个想法”拆成可执行项目，承接小企业和产品 Demo 咨询。

选题方向：

| 优先级 | 选题 | 判断 | 下一步 |
|:--:|:--|:--|:--|
| P0 | 老板有一个产品想法，第一步不是找程序员 | 强定位，适合作为系列开头 | 写稿前先做选题评审 |
| P0 | 一个 App 第一版应该砍掉哪些功能 | 适合小企业客户 | 用“别一上来做全家桶”表达 |
| P0 | 小企业做管理系统，第一版怎么控制成本 | 商业咨询价值高 | 可引流企业系统需求 |
| P1 | 硬件项目为什么要先做 Demo，再谈量产 | 符合老陈嵌入式身份 | 可强化专业背书 |
| P1 | 上位机、嵌入式、App、后台到底怎么配合 | 专业但可讲清 | 注意别讲太技术 |
| P2 | 一个机器人项目怎么拆成机械、电控、软件、测试 | 受众窄但高客单 | 暂作储备 |

表达原则：

- 不讲“大而全方案”，只讲第一版怎么落地。
- 强调先验证，再扩展。
- 强调砍需求、控成本、控风险。
- 让客户觉得“我可以先找老陈把需求说清楚”。

#### 栏目 E3：毕设和小项目决策

作用：承接早期现金流，但不能破坏老陈账号专业感。

选题方向：

| 优先级 | 选题 | 判断 | 下一步 |
|:--:|:--|:--|:--|
| P1 | 毕设选题怎么判断难不难 | 需求明确 | 注意合规表达 |
| P1 | 单片机毕设为什么很多人卡在调试 | 符合嵌入式身份 | 可做专业背书 |
| P2 | App 毕设和小程序毕设哪个更适合普通学生 | 搜索型选题 | 小红书也可复用 |
| P2 | 管理系统毕设最容易踩哪些坑 | 标准化服务入口 | 先储备 |

表达边界：

- 重点说方案辅导、项目实现、调试支持、文档整理。
- 不做不合规承诺。
- 不要让账号变成“代做毕设广告号”。

#### 引流转化路径

内容不是只追播放量，要看是否带来有效咨询。

标准路径：

1. 视频讲一个具体外包坑或产品拆解场景。
2. 评论区引导用户说清项目类型。
3. 私信用标准问题收集需求。
4. 进入项目评估表。
5. 判断能不能接、值不值得接。
6. 输出简单方案和报价。
7. 成交后进入交付流程。
8. 项目结束后隐去信息，沉淀为新案例和新选题。

私信标准问题：

- 你要做的是毕设、小企业项目，还是产品 Demo？
- 现在有没有需求文档、参考案例或截图？
- 需要交付源码、部署、硬件，还是只要演示？
- 期望什么时候完成？
- 大概预算范围是多少？
- 是否已经找别人报过价？

复盘指标：

- 有效私信数。
- 私信到需求表转化率。
- 需求表到报价转化率。
- 报价到成交转化率。
- 客户类型分布。
- 是否带来高质量案例。

#### 发布节奏

试验期不抢主线：

- 每周 1 条商业引流内容。
- 每 3 条程序员职场内容后，最多插入 1 条商业引流内容。
- 优先发布“技术外包避坑”和“产品落地拆解”，毕设类内容作为补充。
- 连续 4 条商业引流内容没有有效咨询，就暂停复盘，不继续硬发。

启动条件：

- 程序员职场主线每周执行不受影响。
- 至少准备 6 条试验线选题。
- 私信承接问题和项目评估表先准备好。

暂定首批测试选题：

1. 老板别一上来就问“做个 App 多少钱”。
2. 软件外包为什么最后容易烂尾。
3. 一个 App 第一版应该砍掉哪些功能。
4. 硬件项目为什么要先做 Demo，再谈量产。
5. 熟人开发也要写清楚交付范围。
6. 小企业做管理系统，第一版怎么控制成本。
